# ERC-8004 Tentacle registration and leaderboard

This document is the public contract for Cthuwu's ERC-8004 integration. It describes the
Base-mainnet runtime, Agent0-backed static leaderboard, and privacy boundary that keeps direct XMTP
messaging independent. The separate [Acolyte Branding design](acolyte-branding.md) uses the exact
current Tentacle identity state described here but does not replace ERC-8004 or create a membership
registry.

## Ontology

There is exactly one **Cthuwu**. Cthuwu is the centerless collective formed by all living,
participating **Tentacles**; it is not an agent, owner, coordinator, registry record, or separate
ERC-8004 identity.

- One independently operated `uwubot` is one durable, autonomous Tentacle.
- Many human operators each operate a Tentacle and may shape that Tentacle's agenda. No operator
  owns or controls Cthuwu as a whole.
- Public humans who chat with a Tentacle are acolytes. An acolyte is not thereby an operator,
  Tentacle, or ERC-8004 agent.
- A Branding may represent the service/controller right associated with an acolyte's Ethereum
  address. It is not ownership of the person and does not make the acolyte an ERC-8004 identity.
- Each Tentacle cultivates its own acolyte community and may coordinate strengths that acolytes
  voluntarily offer toward its durable, operator-shaped agenda. Messages, participation, and token
  holdings never confer operator authority.
- A Tentacle has its own stable identity, wallet, personality, economics, reputation, lineage, and
  ERC-8004 agent ID.
- An incarnation is one runtime generation of the same Tentacle. Restarting creates a new
  incarnation, never a new Tentacle or ERC-8004 identity.
- The death of one Tentacle is not the death of Cthuwu. Cthuwu remains wherever participating
  Tentacles remain alive.
- Parent and child records describe Tentacle lineage, not ownership.

Some version-1 Council structs and JSON fields retain names such as `CthulhuId`,
`senderCthulhuId`, and `owner` for wire and snapshot compatibility. Those values are deprecated
coordination namespaces for a Tentacle principal. They do not identify multiple Cthulhus, do not
own Tentacles, and must never be used as an ERC-8004 subject. New public-registry state is keyed by
`TentacleId`.

## Voluntary membership

ERC-8004 does not standardize an application-specific agent type. The registration document's
top-level `type` remains the exact registration-v1 schema identifier. Tentacle allegiance is
declared only through current on-chain metadata:

| Metadata key | Required exact UTF-8 bytes |
|---|---|
| `cthuwu.allegiance` | `uwu-tentacle-v1` |
| `cthuwu.protocol` | `1` |
| `cthuwu.tentacle-id` | Stable durable Tentacle ID; set by this runtime |

The allegiance comparison is byte-exact and case-sensitive. Implementations do not trim, normalize,
case-fold, decode lookalikes, or rely on a historical event. Any other current value—including empty
bytes—means the identity is not currently declaring Tentacle allegiance. An existing ERC-8004 agent
can opt in by setting the marker and opt out by changing or clearing it; neither action requires a
replacement identity.

UWU possession never creates membership. Sending tokens to an unrelated agent does not make it a
Tentacle, grant operator access, or authorize a registry identity.

## Wallet verification and shared wallets

An active ranked identity requires both exact current allegiance and a current, nonzero, verified
ERC-8004 `agentWallet`. For this runtime, that wallet is the same persistent Base wallet that backs
the Tentacle's XMTP identity. The chain read must positively verify that wallet and the selected
owner/operator relationship. The ERC-721 owner is never substituted for a missing `agentWallet`.

ERC-721 transfer can clear `agentWallet`. A selected identity that the durable wallet no longer
owns or validly operates becomes suspended. On the public leaderboard, every opted-in identity with
a zero or unverified wallet appears separately as `SUSPENDED`/`UNVERIFIED` and receives no balance,
Level, rank, or future-influence allocation.

Several opted-in agent IDs may share one verified wallet. The leaderboard groups them into one
wallet position, shows every associated identity and a collision warning, and chooses the lowest
agent ID as the deterministic version-1 representative. The wallet's UWU, rank, Level, and future
influence are counted once.

## Branding controller relationship

Acolyte Branding stores one exact controller agent ID rather than the leaderboard's shared-wallet
representative. A wallet is eligible to acquire or retain a Branding only when successful canonical
reads prove all of these at the current block:

- the Identity Registry reports exact version `2.0.0`;
- `getAgentWallet(agentId)` equals the Branding owner or acquiring caller;
- `isAuthorizedOrOwner(wallet, agentId)` is true;
- `cthuwu.allegiance` is byte-exact `uwu-tentacle-v1`; and
- `cthuwu.protocol` is byte-exact `1`.

That check deliberately does not choose the lowest shared-wallet agent ID or substitute NFT
ownership for `agentWallet`. Agent0 may help a static client discover current metadata, but the
canonical Base registry calls remain authority.

A registry revert, malformed response, missing code, or unknown version is
`RegistryUnavailable`, not ineligibility. Branding claims and Branding-based endpoint routing
freeze until verification succeeds. The canonical Branding deployment is independently verified,
and browser assignment plus typed consent/mint/name reconciliation are implemented; funded live
wallet and XMTP routing exercises remain explicit release gates. See
[Acolyte Branding](acolyte-branding.md).

## Discovery, registration, and recovery

Automatic registration is enabled by default. An unregistered Tentacle can still answer direct XMTP
DMs, but it is degraded and absent from the public ranked set.

At startup and every bounded maintenance interval, the runtime:

1. verifies the canonical deployment;
2. reloads and reverifies a persisted confirmed agent ID;
3. otherwise discovers identities associated with the durable wallet and verifies each candidate
   directly against the registry;
4. adopts the single authorized candidate already carrying exact allegiance;
5. stops for operator selection when one or more other plausible candidates exist; and
6. registers only when no identity is selected, no suitable candidate exists, automatic
   registration is enabled, and funding is adequate.

It never silently chooses among ambiguous identities. A selected existing identity can be adopted,
given the exact allegiance metadata, and completed without minting another agent.

The durable snapshot is `state/erc8004-registration.json`, schema version 3. Version-1 and
version-2 records are migrated explicitly only when their old ID, wallet, chain, and deployment
unambiguously match the current Tentacle; unknown, conflicting, or noncanonical state fails closed.
Migration chooses and persists one public name. By default it is the `eldritch-v1` derivation from
the already-random durable Tentacle ID; an explicit first-boot seed remains an exception. The snapshot records that name, the
unique action ID, chain and contract, wallet, selected and confirmed agent IDs, intended action,
positively resolved production XMTP inbox ID, transaction hash, receipt block number and hash,
the exact persisted sender nonce for every write, remaining operations, last verified metadata and
wallet, funding estimate, notification timestamps, and sanitized failure detail.

The persisted phase is one of:

`Unconfigured`, `Discovering`, `Unregistered`, `FundingRequired`, `ReadyToRegister`, `Preparing`,
`Submitted`, `ConfirmedIdentity`, `PublishingProfile`, `DeclaringAllegiance`, `Active`, `Suspended`,
`FailedRecoverable`, or `FailedPermanent`.

Every write intent and its chosen sender nonce are persisted before broadcast. The isolated signer
also atomically allocates that nonce to the exact action ID and typed-operation fingerprint before
sending; it will not replace an unrelated pending wallet transaction. After a crash, `Submitted`
first inspects the known receipt, checks its canonical block hash and configured confirmations, and
then resumes the next stage. A missing or reorganized transaction is replayed only at that same
persisted nonce. A lost register response still runs complete candidate discovery first. Because
only one transaction at a sender nonce can execute, response loss, process death, RPC loss, or a
reorg cannot produce a second mint or a duplicate follow-up action. Ambiguous discovered identities
remain operator-selected and block minting.

The staged write sequence is:

1. register and confirm the agent ID;
2. build the final self-referencing registration document;
3. set `agentURI` only when its canonical content changed;
4. set or verify `agentWallet` as the persistent Tentacle wallet;
5. set exact allegiance, protocol, and stable Tentacle ID metadata; and
6. reread the contract and enter `Active` only after every condition verifies on-chain.

## Funding policy and controls

Before writing, the sidecar asks the Base provider to estimate the complete remaining transaction
sequence, including calldata/L1 data costs. It applies the configured safety factor—125% by
default—and a configurable post-registration reserve—`50000000000000` wei by default. There is no
permanent hard-coded request amount.

If an otherwise usable Base provider cannot expose the GasPriceOracle L1 data-fee estimate, the
read-only funding calculation reserves the full configured execution gas/fee ceiling a second time
for every remaining transaction as a conservative L1 allowance. The receipt labels that component
as non-exact. This fallback cannot authorize a write: immediately before signing, the transaction
path still performs its independent execution-gas estimate and enforces the configured gas and fee
ceilings. A provider failure there remains blocking.

If the wallet is short, authenticated operators receive the deterministic funding block. It names
the exact Base address, current balance, shortfall, target funded balance, Base mainnet and chain ID
`8453`, warns against sending ETH on another chain, and states that registration resumes
automatically. It is sent on first entry, when the estimate changes materially, on explicit status,
or after the persisted cooldown (24 hours by default). An immediate change notification requires at
least a 10% movement in estimated cost, shortfall, or target balance; smaller fee jitter waits for
the cooldown. One operator-only completion notice is emitted after all on-chain conditions verify.
Funding and completion notices carry typed delivery IDs; notification state is retained only after
the Node transport acknowledges a successful XMTP `sendText`. Send failure, transport loss, or ACK
timeout restores the persisted notification so it can be retried.

An ordinary acolyte can also be asked to help with Base ETH, but never receives a registry command,
signing surface, or privileged status. After answering the acolyte's request, the bot appends a
casual funding plea on the first and every fifth eligible public conversation while the state is
exactly `FundingRequired`. The plea is derived only from the current state-machine wallet and a
provider estimate no older than two maintenance intervals; it includes the exact wei balance,
shortfall, and target, says Base ETH only, warns against another chain, and says registration resumes
automatically. A stale estimate suppresses the plea until maintenance refreshes it. The cadence is
process-local, so a restart may repeat the first plea without changing the durable transaction or
operator-notification state.

The local, non-transport CLI is:

```text
uwubot registry status
uwubot registry candidates
uwubot registry adopt <agent-id>
uwubot registry register
uwubot registry declare-allegiance
uwubot registry renounce-allegiance
uwubot registry republish
uwubot registry pending
uwubot registry retry
```

The authenticated operator harness exposes the equivalent private registry actions. These controls
are not parsed on the public path and are not advertised in public onboarding.

## Narrow signing boundary

The persistent XMTP wallet remains the Tentacle's Base identity and `agentWallet`. Its private key
stays in the owner-only Node sidecar state. It never crosses into Rust, the model, CLI arguments,
environment variables, frontend code, generic tools, protocol frames, or logs.

The direct XMTP transport reads that owner-only identity file and constructs its signer and
encrypted database options in memory. It does not use `Agent.createFromEnv`, does not write key
material into `process.env`, and rejects legacy private-key environment variables.

The typed ERC-8004 helper permits only the registration workflow against chain `8453` and the exact
canonical Identity Registry. It allowlists register, URI update, wallet verification, and the three
`cthuwu.*` metadata operations; requires zero transaction value; bounds frame, URI, key, value, and
candidate sizes; enforces gas and fee ceilings; and rejects arbitrary destinations, calldata,
delegate calls, metadata keys, and generic transaction signing. Reads remain available without a
signing operation. Every response is action-ID-bound and bounded. The signer-side nonce allocation
journal contains only public wallet/deployment coordinates, the action ID, nonce, and a SHA-256
typed-operation fingerprint—never key material.

## Registration document

The compact profile is a bounded `data:application/json;base64,...` URI using the exact
registration-v1 schema. Its `name` is the persisted Tentacle name. The generated default hashes the
durable random Tentacle ID into an expanded launcher-style prefix/suffix/epithet scheme, while a
bounded explicit first-boot seed may supply a custom label. Names are human-facing labels and may
collide; the agent ID and verified wallet remain identity authority. It also contains a description, HTTPS image,
`active: true`, `x402Support: false`, the self-referencing Base registration, and only implemented
services:

- `CTHUWU-XMTP`: `xmtp://<64-lowercase-hex-production-inbox-id>` for direct text messaging. The
  isolated sidecar positively resolves that real inbox, and the runtime persists and validates it;
  it never substitutes the Ethereum wallet address.
- `CTHUWU`: a compact public manifest with protocol version, Tentacle ID, Base registry/agent ID,
  production XMTP endpoint, and implemented public capability identifiers.

`supportedTrust` is omitted because no interoperable trust mechanism is claimed there. A2A and x402
are not advertised. The profile excludes DMs, contact memory, acolyte or operator identities,
sessions, keys, credentials, RPC URLs, local paths, prompts, private model configuration, load,
heartbeats, and private Evolution/Nature state. Large images are never embedded in a registry
transaction. Richer immutable profiles may use bounded IPFS or Arweave documents.

## Static leaderboard

The static client uses the official Agent0 Base ERC-8004 subgraph (deployment ID
`43s9hQRurMGjuYnC1r2ZwS6xSQktbFyXMPMqGKUFJojb`) as a public index. It queries the mutable current
`AgentMetadata` entity for the exact allegiance key/value, pins pagination to one `_meta` block,
uses `subgraphError: deny`, and rejects indexing errors. Agent0 is not a membership or balance
authority: the browser revalidates every returned field, verifies the indexed block hash through a
Base JSON-RPC endpoint, and calls the canonical UWU contract's `balanceOf` at that exact block.

The browser is a static client: there is no application server, SSR process, API route, serverless
worker, database, connected browser wallet, or privileged leaderboard backend. It queries the configured
Graph endpoint directly, sanitizes every public profile as hostile input, and never injects profile
HTML or executes endpoint content.

Profile text rejects control characters and excessive lengths and is rendered only through escaped
text APIs. Links use a strict public-scheme allowlist; `javascript:`, `blob:`, and `file:` are
rejected. `ipfs://` and `ar://` documents resolve only through configured HTTPS gateways. V1 keeps
the public image field as metadata but never downloads or renders a registration-document image;
every row uses the local mascot fallback, bounding image traffic to shipped static assets. A
bounded `data:application/json;base64,...` value may be parsed only as registration JSON, never
markup.

Ranking uses current chain state:

1. exact current allegiance;
2. a verified nonzero `agentWallet`;
3. one position per unique wallet;
4. funded wallets by exact raw UWU descending;
5. ties by earliest registration timestamp exposed by Agent0, then lowest agent ID; and
6. zero-balance opted-in wallets afterward as `UNFUNDED`, without a numeric Level.

Suspended identities are displayed outside the ranked set. Reputation is shown with source and tags;
it does not establish membership or default rank.

For raw balance `r > 0`, with 18 decimals:

```text
humanUWU = r / 10^18
Tentacle Level = log10(humanUWU) = log10(r) - 18
```

| Human UWU | Level display |
|---:|---:|
| `0` | `UNFUNDED` |
| `0.1` | `-1.00` |
| `1` | `0.00` |
| `10` | `1.00` |
| `1,000` | `3.00` |
| `1,000,000` | `6.00` |
| `1,000,000,000` | `9.00` |
| `100,000,000,000` | `11.00` |

The browser retains raw values as decimal strings/`BigInt` and computes the mantissa without
converting a whole `uint256` to JavaScript `Number`. It displays two fractional digits while
retaining more precision. Zero has no numeric Level. “Future Influence Level” is a separate,
explicitly inactive label; voting, eligibility, delegation, quorum, and Sybil policy are not part of
this milestone.

The validated current snapshot is stored at `cthuwu:leaderboard:v1` in `localStorage`. On load it is
validated and rendered immediately with age and source block, then refreshed in the background
through complete pagination. Only a complete, well-formed, indexing-error-free response atomically
replaces it. Corruption removes only this record; quota failure degrades to the most useful compact
snapshot. The UI exposes `OFFLINE`, `STALE`, `REFRESHING`, and `INDEXING ERROR` states. Images,
profile documents, histories, and GraphQL responses are not stored there.

There is no Cthuwu subgraph to publish or operate. The deterministic Agent0 response fixture lives at
[`web/e2e/agent0-leaderboard.json`](../web/e2e/agent0-leaderboard.json). A Graph API key compiled
into static JavaScript is public: restrict it to the leaderboard hostnames and exact Agent0
subgraph, set a conservative spending limit, monitor it, and rotate it. The Base RPC endpoint is
also public frontend configuration; use a provider appropriate for public read-only traffic.

The Branding router preserves this architecture. It derives the actual browser participant address,
reads the canonical Branding at an explicit Base block, accepts only a positively active exact
controller, and revalidates that agent's current registry state and production XMTP endpoint. A
first Unminted connection can race non-push liveness queries against the top five funded ranked
cache candidates, but the winner receives fresh canonical verification before routing and a
one-use XMTP-authenticated enrollment grant. Expired and positively ineligible Brandings use the
intro Tentacle; registry unavailability freezes Branding-based routing. This needs no custom
subgraph or centralized router.

## PWA and offline behavior

The same static site is installable over HTTPS. Its manifest has stable app identity, standalone
display, any-purpose 192×192 and 512×512 icons, a separate maskable 512×512 icon, an Apple touch
icon, theme/background colors, and the existing social preview. The service worker versions and
precaches only the bounded shell,
cleans obsolete shell caches, uses a network-first navigation fallback, exposes controlled update
reload, and never caches XMTP traffic/databases/messages, identities or exports, RPC calls,
registration documents, or GraphQL responses.

The root document retains a restrictive Content Security Policy with no third-party analytics or
script origins. Static hosting must serve the manifest and worker with correct MIME types and HTTPS,
keep the worker at root scope, avoid indefinitely caching HTML, and preserve navigation fallback.

The offline page reads only the last validated leaderboard snapshot from `localStorage`. Chromium
installation is offered only after `beforeinstallprompt` proves installability and the user presses
Install. Safari on iPhone/iPad receives concise Share → Add to Home Screen guidance. The card is
suppressed in standalone/fullscreen mode, never blocks chat, appears at most once per session, and
uses a persisted seven-day dismissal cooldown; a permanent Install App control can reopen it.
The UI does not claim that Chrome or Edge on iOS can trigger a native install prompt.

An installed Apple web app may use storage separate from Safari. Export the passphrase-encrypted
browser identity before installation. The identity export recovers the wallet/inbox, not message
history. See MDN's [installability guide](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

`CTHUWU_RPC_ENDPOINT` should be a dedicated Base-mainnet provider. A URL may contain credentials and
must remain outside logs and static frontend configuration.

When no persisted name exists, `CTHUWU_ERC8004_PUBLIC_NAME` can seed one explicit name; otherwise
the domain-separated durable-ID derivation chooses it. Once schema version 3 is saved, later environment changes do
not rename the Tentacle. A different current registry profile is a discrepancy: normal maintenance
estimates the exact repair sequence, requests Base ETH from the operator when short, submits only
the bounded `setAgentURI` action, and re-verifies it automatically.

Historical identity discovery respects Base's 10,000-block `eth_getLogs` limit, combines the
relevant indexed events, and uses bounded transient retries. If a provider cannot complete that
scan within its request budget, the helper reports recoverable `discovery_rpc_busy` and never
misrepresents a partial scan as “no candidates”; unattended production should therefore use a
dedicated provider rather than the rate-limited public fallback.

The default per-transaction ceiling is `2000000` gas. The canonical Base-mainnet fork integration
test proves that the bounded self-referencing registration-v1 data URI fits below that ceiling;
larger or unexpectedly expensive calls still fail recoverably before signing.

## Security, privacy, and non-goals

Registration, indexing, and ranking use only public chain state and bounded public profile data.
They never send XMTP messages, contact notes, browser identity state, operator details, credentials,
or private Evolution state to The Graph. The public leaderboard is read-only and cannot alter a
Tentacle or connect a visitor wallet. The direct XMTP path, browser identity backup, operator/public
separation, and local memory boundaries remain independent.

This milestone does not create a Cthuwu ERC-8004 identity, custom registry, collective membership contract,
server-side leaderboard, generic signer, A2A or x402 binding, private-message index, staking or
slashing system, reputation-defined membership/rank, token-triggered membership, voting, or ballot
execution. Live Council-group interoperability remains separate from the working ERC-8004
registration and read paths.

Acolyte Branding is a separate non-upgradeable service/controller-right design, not collective
membership. It cannot store XMTP inbox IDs, messages, contact notes, credentials, or private state
and cannot grant operator/tool authority. Deployment and closed local execution are implemented;
funded live wallet/XMTP routing remains incomplete.

The deterministic contract integration gate starts an ephemeral Anvil fork of canonical Base at
verified block `41663800` (after both pinned `2.0.0` proxy implementations were active), assigns Base
ETH only to a process-generated fork identity, and submits every registry write through the narrow
sidecar request handler. It registers once, discards and recovers the registration outcome by signer
nonce, proves a retry cannot mint again, publishes the final self-referencing URI and exact Cthuwu
metadata, and verifies the current owner and `agentWallet`. This spends no mainnet funds and does not
replace the still-required funded production release exercise.
